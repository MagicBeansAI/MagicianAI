# Magicutor Extension Architecture

## Current Shape

Magicutor is now a CDP proxy plus WebSocket bridge for the Chrome extension. It
exists so `agent-browser` can automate the user's normal Chrome profile through
the extension's `chrome.debugger`, `tabs`, `windows`, `downloads`, and
`tabCapture` permissions.

The extension does not talk to a Chrome native messaging host. It assumes
Magician and Magicutor are already running.

## Runtime Flow

```text
Extension popup/side panel
        |
        | POST /api/magician/v2/executions
        | POST /api/magician/v2/executions/{id}/start
        v
Magician outer loop
        |
        | browser capability -> inner loop
        v
agent-browser --session magician-{execution_id}
        |
        | ws://127.0.0.1:3003/devtools/browser/magician-{execution_id}
        v
Magicutor CDP proxy
        |
        | /bridge/native WebSocket envelope
        v
Extension background worker
        |
        | chrome.debugger CDP commands and Chrome extension APIs
        v
Chrome tabs/windows in the user's profile
```

## Thread Ownership

Magicutor scopes browser access by agent-browser thread id:

- Dedicated runs lazily create a Chrome window when `Target.getTargets` is first requested.
- "Use this tab" runs call `POST /cdp/threads/{thread_id}/bind-tab` and expose only that tab plus opener-chained tabs later claimed by CDP target events.
- Tabs outside the thread's owned set are invisible to `agent-browser`.
- `DELETE /cdp/threads/{thread_id}` clears owned-tab state and closes dedicated windows; bound user tabs are not closed by this endpoint.

## CDP Session Routing

The proxy mediates between agent-browser's WebSocket and the extension's `chrome.debugger`. Two kinds of session ids flow through the `CdpSession` actor and are tracked separately because Chrome's debugger recognises only one of them:

- **Main-tab session uuid** — minted locally by the proxy in the `Target.attachToTarget` handler (`Uuid::new_v4()`) and handed back to the client as the attach response's `sessionId`. The client uses it on every subsequent command for that tab. Chrome itself never sees this id — it was generated by Magicutor.
- **OOPIF iframe sessionIds** — auto-emitted by Chrome via `Target.attachedToTarget` events when the parent debugger has `Target.setAutoAttach({filter: [{type: "iframe"}]})` (the extension turns this on at attach time). These are real Chrome ids that `chrome.debugger.sendCommand` will accept as a `sessionId` field for sub-target routing.

Both go into `CdpSession.sessions: HashMap<String, i32>` (sessionId → tabId) so any inbound command resolves to the right tab. The `iframe_session_ids: HashSet<String>` discriminator records which of those ids are iframe-origin — only those get forwarded as the `sessionId` field on the `debugger_command` bridge message. Main-tab commands forward without a sessionId; Chrome targets the tab's implicit main session, which is what we want.

Mistakes here are operator-visible: a previous version of this filter forwarded every registered sessionId, including the proxy-minted main-tab uuid, and Chrome's debugger rejected every command with `-32001 "Session with given id not found"`. The fix sits in `update_iframe_sessions_from_event` (registration) and the `forward_session_id` filter in the main command handler.

## Active Extension Surfaces

- `popup.html` / `sidepanel.html`: goal input, run/resume/stop controls, current-tab binding toggle. Both surfaces share `panel_tabs.js` (`setupPanelTabs` over `[data-panel-tab]`/`[data-panel-view]` + `wireCollapsibleStatus` for the collapsible "Server Ready" header). Tabs: Control (automation + activity), Settings (overlay/debug settings + ambient pairing), and — side panel only — Live (preview).
- `control_panel.js`: UI state and start/stop/resume button wiring. The current/recent action feed renders raw CDP `debugger_command` traffic as one-line method summaries with compact payload tooltips.
- `extension_messages.js`: Magician execution API calls, CDP thread binding, polling, overlay lifecycle.
- `background.js`: WebSocket bridge connection, bridge action dispatcher, tab/window/debugger implementation. Raw `debugger_command` traffic from agent-browser is forwarded unchanged to `chrome.debugger`, including JavaScript dialog events and commands. Input/navigation/screenshot commands are mirrored into the visual overlay so CDP-proxy runs still show the floating status panel, cursor sprite, and Stop control.
- `actions_tabs_windows.js`: tab/window inventory for CDP target discovery. The default `list_tabs` path must stay independent of `chrome.debugger.getTargets()` because that Chrome API can hang; foreign-debugger rejection happens during bounded `chrome.debugger.attach` instead.
- `tabs.js`: session-tab tracking for opener-created tabs.
- Thread-owned automation page signals are mirrored by the CDP proxy from foreground automation commands/events and drained through `/ambient/page/drain/{thread_id}` without an extra debugger command. The old extension-side CDP page fingerprinting module was removed because it issued its own `chrome.debugger.sendCommand('DOM.getDocument')` and could contend with foreground automation.
- `ambient_collector.js`: always-on, principal-keyed ambient browsing capture — the user-owned lane, distinct from the thread-owned automation page-signal drain. Queues redacted signals in `chrome.storage.local` and HTTP-batches them to `POST /ambient/signals/batch`, attaching the `X-Collector-Token` issued at pairing so the server resolves the capture scope from the token (the extension never asserts a principal). The pairing field — present in **both** the popup and the side panel, wired by the shared `ambient_pairing.js` (`wireAmbientPairing`) — stores that token; incognito and denylisted origins are excluded client-side. (`background.js`'s general `onMessage` listener must `return false` for `weg_*` messages so the dedicated collector listener owns the response, else the pairing UI shows a false "Pairing failed".)
- `live_preview_background.js`: live preview source discovery by execution/thread. Debugger-backed automation tabs stream through CDP `Page.captureScreenshot` polling; non-debugger tabs retain the `tabCapture`/offscreen fallback.
- `notes_capture_menu.js`: the selection-only "Save selection to Magician Notes" context item. A sibling of the Contextual Assist item rather than a mode of it — sharing an entry would make the common case (keep this, do nothing else) a two-step interaction. It posts straight to Magician's `/notes/capture-selection` through `magicianFetch`, so the opaque bearer chooses the principal/workspace and the payload carries no scope assertion. Each click carries a fresh `capture_id`, so a resend after a lost response is filed once while a genuine second capture is filed again.

## Removed Legacy Surfaces

- Native messaging host mode and stdio framing.
- `ExtensionExecutor` and Rust-side action execution.
- `/execute`, `/sessions`, and `/events` Magicutor APIs.
- Native Chromium/chromiumoxide executor.
- Generated-action registry and sandbox in Magicutor.
- Extension-local observe support: selector/coordinate action helpers, event-listener instrumentation, observe network/console context buffers, and the old extension-local trace buffer.
- Extension-side JavaScript dialog pending state and auto-dismiss logic. Alert/confirm/prompt handling belongs to agent-browser's CDP dialog commands.
- Legacy extension tab-stack compatibility helpers. Active browser ownership is session/thread based.
- `content-script-early.js` main-world download interception (removed in Magician v0.6.683).

Historical docs and changelog entries may still mention those surfaces, but
they are not part of the current runtime.
